Large migration dispatch

/batch 把一次大改动拆成一排独立 PR

它先停在计划和验收。用户批准以后，主 Claude 才把 5 到 30 个能单独合入的工作单元一次发给后台 worker。每个 worker 在自己的 git worktree 里改、查、测，随后各开一份 PR。主会话收回网址和失败原因，最后停在汇总表。OL

01 · TERMS

读懂这页只要三个词

三者各有自己的边界。/batch 负责把它们接成一套编排流程，底层机制仍由 Claude Code 的 skill、subagent 和 git worktree 提供。OL

Bundled skill

随 Claude Code 一起提供的提示说明。它把详细步骤交给主 Claude 执行，没有另起一套固定脚本状态机。OL

Background subagent

主会话派出的独立上下文。worker 自己使用工具，结束时只把最终文本交回父会话。O

Git worktree

同一仓库的独立工作目录和分支。并行 worker 的文件改动互不落进对方目录。O

02 · SEQUENCE

公开契约里的五步

以下只保留官方 Commands 页面承诺的产品流程。O

01用户输入

在 Git 仓库里输入 /batch 和大改动说明。

02调研与拆分

Claude 调研代码库，把工作拆成 5 到 30 个可独立实现的单元。

HOLD展示计划

计划先交给用户审阅；批准以前不启动实现 worker。

03隔离执行

批准后，每个单元由一个后台 subagent 在独立 worktree 中实现和测试。

04分别交付

各单元分别创建 Pull Request，主会话汇总每个单元的结果。

03 · FLOW

一个计划，多个隔离结果

主会话负责计划和汇总；worker 有独立上下文与独立 worktree。公开文档没有把内部任务信封或输出令牌定义为稳定接口。O

用户说明目标和范围
主会话计划5–30 个独立单元
隔离 worktree各自实现和测试
独立 PR分别供审查与合入
结果汇总成功或失败状态
04 · LIMITS

计划批准不等于权限放行

模型连接、GitHub 交付、Claude Code 权限和仓库规则仍分别生效。O

输入与仓库

命令需要任务说明，并要求当前目录属于 Git 仓库。

批准门

用户没有批准计划时，不进入后台实现阶段。

执行权限

worker 的文件、Shell、网络与 Git 操作仍按权限规则逐次判断。

账户与费用

并行模型调用消耗当前订阅额度或 API、云平台 token 用量。

GitHub 交付

创建 PR 需要有效身份、可推送分支和仓库允许的 PR 路径。

07 · UNKNOWNS

说明写得很细，运行时仍有四件事未知

它们会改变读者对规模、失败和可恢复性的判断，所以保留在页面上。

拆分服从度

真实仓库里是否总会得到 5 到 30 个互不重叠、能单独合入的单元。

运行时并发

同一消息放出 30 个 worker 后，底层怎样排队、限流和退避。

部分失败

某个 worker 卡在权限、网络或 branch protection 时，其他 worker 和最终表怎样收敛。

恢复与清理

计划文件的确切保存期，以及已推送 worker 的 worktree 在 2.1.247 何时清理。
