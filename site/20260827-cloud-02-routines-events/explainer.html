01 · terms

先认四样东西

本页讲一条调度链，只保留读懂它所需的名词。云 session 的一般接管与环境管理留给相邻页。

Routine O

保存在个人 claude.ai 账户里的配置。它带着已写好的 instructions、仓库、模型、环境和 connectors，等待触发器。

Trigger O

启动条件。一个 Routine 可以同时接受 schedule、带 token 的 API 请求和筛选后的 GitHub 事件。

Run session O

一次触发对应的一条完整云 session。GitHub 的两个更新会变成两条独立 session，不会接着同一段对话跑。

Environment O

这次 run 的运行条件。它约束网络，提供变量、API credentials 与 setup script。Anthropic 托管时，每条 session 使用新的 Linux VM。

可用套餐 O

Routines 面向 Pro、Max、Team 与 Enterprise。账户还要启用 Claude Code on the web，Team 和 Enterprise 组织另受 Routines 开关约束。

CLI 登录 O

/schedule 要求 claude.ai 订阅登录。Console API key、Anthropic profile、federation credential 和云提供商登录都不能使用这个入口。

Enterprise 与 API O

Enterprise 用户需要 Premium 或 Chat + Claude Code 席位。fire API 使用 Routine 专属 bearer token，不接受 Claude API key。

02 · sequence

一次触发怎样走完

这条时序把用户动作、云端角色与停止点排在同一条线上。每一步附近的证据标记与 evidence.md 保持一致。

00

保存工作说明

用户写清目标，选择模型、仓库、环境与 connectors，再挂一个或多个 trigger。配置留在个人云账户。 O

01

事件到达

schedule 到点，API fire 通过认证，或 GitHub 事件满足全部 filter。未匹配、暂停或超限会停在这里。 O

02

创建新 session

每次成功触发都会建立一条新 session。API 在创建后立即返回 URL，不等任务完成。 O

03

准备云环境

托管运行拿到新 VM，clone 仓库，复制环境变量。setup 结果若命中缓存，脚本可能不再重跑。 O

04

自主执行

保存的 instructions 成为 assigned task。运行中没有批准对话，可用范围早已由环境、仓库和 connectors 定下。 O

05

留下可检查结果

run 进入历史列表。用户打开 session 看 transcript、diff 与错误，也可让 prompt 指示 connector 把摘要发出去。 O

03 · flow

数据从哪里来，又去了哪里

固定配置与本次事件分开进入 run。这个区别决定了权限判断，也决定 API payload 为什么不会直接变成命令。

预先保存

  • instructions 与模型
  • 仓库与 trigger
  • 环境与 connectors

O 这些内容由已授权账户提前保存。

→

新 run session

  • 默认分支 fresh clone
  • 启动时复制环境变量
  • API text 进入不可信包装

O prompt 要明确引用 fire payload，Claude 才按其中信息行动。

→

运行产物

  • session transcript 与 diff
  • claude 前缀分支与 PR
  • connector 写入的外部结果

O 外部动作使用用户已连接的身份。

关键读法　绿色 run 只说明 session 没有基础设施错误地启动并退出。任务可能仍被网络挡住，缺 connector 工具，或自己判断无法完成。要打开 run 才知道。 O

04 · limits

停在哪里，怎样再试

触发入口、session 内部与整次 run 是三个重试层。把它们写成一个自动恢复故事，会掩盖重复执行的风险。

触发前就被挡住

Routine 暂停、token 错误、组织关闭功能、环境已归档或账户用量到顶，都可能让新 session 根本不出现。

400 · 401 · 403 · 429 O

事件被直接丢掉

GitHub webhook 超过每条 Routine 或每账户的小时上限后，事件会丢弃到窗口重置。这里没有补跑承诺。

event dropped O

session 启动后失败

环境网络、仓库权限、setup、工具或 prompt 本身都可能失败。绿色状态仍可能出现，任务结果要读 transcript。

task result differs from infra status O

API 调用方重试

500 适合指数退避，503 适合短暂等待，429 要遵守 Retry-After。一次请求若已经成功，再发一次会创建另一条 session。

no idempotency key O

session 内请求重试

Claude Code 一般会重试可恢复的模型 API 故障。本页没有真实云 run，无法确认托管 Routine 的每项参数都与本机一致。

request level only O I

整次 run 再跑

官方给出 Run now 与 `/schedule run` 的手动入口，没有公开整次失败后的自动重跑次数、退避与去重契约。

manual path documented O I

所在层官方已说明仍需防的事
触发 HTTP500、503、429 的等待方式没有幂等键，成功后的重复提交会多开 session
Claude 请求可恢复 API 故障的一般自动重试工具已经执行时不能粗暴重放整个请求
完整 run用户可以手动 Run now自动重跑与去重规则未知

05 · experiment

这页为何停在 documented

本机证据证明版本快照存在，云端主链来自官方契约。创建真实 Routine 会动用私人账户和订阅用量，本轮没有越过这条线。

L
ONLY

本机安装目录仍保留 Claude Code 2.1.247。版本输出和二进制 SHA-256 与固定基线相符。该版本的顶层 help 公开了 --cloud，说明它能创建或连接云 session。 L

研究 shell 的默认 PATH 没有 claude，当前安装软链接也已经升到 2.1.250。本页直接调用固定版本文件，没有让新版本替代研究快照。

没有执行 /schedule、/fire、Run now 或 GitHub webhook。也没有读取账户里的 Routine、connector 或 run transcript。因此本页缺少 R，状态只能是 documented。

06 · implementation

版本与实现边界

这里只写会改变这条生命周期的版本差异。环境的完整配置方式与云 session 的接管行为由相邻页继续解释。

  1. CLI 创建入口
    用 `/schedule` 对话式创建 Routine 需要 2.1.225 或更高。2.1.247 已满足。 O

    ≥ 2.1.225

  2. 运行历史解释
    让 CLI 列近期 runs、打开日志并解释工具错误与最终结果，需要 2.1.227 或更高。 O

    ≥ 2.1.227

  3. 保存 prompt 的身份
    2.1.213 以前，触发 prompt 以不可信后台通知进入，Claude 可能拒绝。当前把预存 prompt 当作 assigned task，API fire text 仍是不可信数据。 O

    changed 2.1.213

  4. 没有 schedule 的显示
    2.1.211 以前，这类 Routine 可能显示公元 1 年的 next run。当前应当显示没有下次运行时间。 O

    fixed 2.1.211

  5. 研究预览
    Routines 与 fire API 都还在 research preview。beta header、请求形状、限额和 token 语义可能变化。 O

    snapshot 2026-08-27

07 · unknowns

还不能写成事实

这些缺口会影响重复执行、告警与恢复设计。官方补齐契约或真实隔离实验完成以前，页面不会替产品猜答案。

调度器内部怎样排队

event accepted 到 session provisioning 之间有哪些持久状态、投递保证与超时，官方没有公开。schedule 的几分钟错峰只说明启动时间，不说明队列实现。 I

整次失败会不会自动重跑

公开材料给了 HTTP 调用方退避和 Claude 请求级重试，也给了手动 Run now。整条 run 的自动重跑次数、去重键与最终停止条件仍未知。 I

完成通知由谁发送

官方保证 run 进入列表，并展示让 connector 发 Slack 摘要的例子。Routine 是否另有邮件、网页或手机完成提醒，文档没有说明。Remote Control 的手机推送不能拿来补这个缺口。 I

GitHub 重投怎样去重

每个匹配事件都会新建 session，小时上限之外的事件会被丢掉。webhook 重投、filter 修改与限额窗口交界处怎样识别重复事件，仍没有公开契约。 I

setup cache 何时失效

官方说明 setup 结果会缓存，也说明 session 使用 fresh clone。缓存精确键、复用范围、失效时机与单次 run 的最长墙钟时间还需单独验证。 I
