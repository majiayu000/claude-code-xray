Agent Team 共用任务列表，各自保留上下文

Lead 拉起具名 teammate。大家各有自己的上下文，却看同一批任务，也能直接互发消息。用户决定收尾时，lead 发出关闭请求；会话退出后，运行配置自动清掉，任务记录继续留在本机。

这条链只在启用实验开关的交互会话里成立。它没有给 teammate 自动分 worktree，也不会让权限批准在 agent 之间代传。

01

四个角色

Lead

主会话。拉人、分工、收结果，最后也由它发起关闭。lead 身份不能移交。

Teammate

独立 Claude Code 实例。拥有自己的上下文窗口和具名地址，只接到项目上下文与拉起时的提示。

Task list

共享任务表。状态只有待领、进行中和完成，负责人和依赖也记在这里。

Mailbox

按 agent 分开的本地 JSON 信箱。普通消息、完成通知和关闭协议都经这里送达。

02

一次 team 的时序

0
隐式 team
O · 2.1.178+

实验开关为 1 时，交互会话已经带着一个 session 级 team。当前版本没有 TeamCreate，也没有自定义第二个 team。

1
拉起成员
O

用户告诉 lead 需要哪些 teammate。lead 用具名 Agent 调用拉起成员。Claude Code 不另弹出建 team 的确认。成员会重新加载常规项目上下文，lead 先前的对话不会跟着过去，分工要求要写进拉起提示或后续消息。

2
生成工单
O

Lead 建任务和依赖。任务先处于 pending，领取后改为 in progress。依赖未完成时，领取入口保持阻塞。共享表让其他成员看见谁正在做什么，也让 lead 找到迟迟没有推进的任务。

3
领取工作
O

Lead 可以指派，teammate 也能自领一个未分配且未阻塞的任务。文件锁处理同时争抢。

4
消息与移交
O + I

成员按名字互发消息。冻结的 2.1.247 会把 idle 通知送到 lead，通知却可能漏掉 teammate 的最终回答。给全组发同一条消息时，发送方仍要逐个投递。官方没有独立 handoff 事务。先用明确消息送出已有发现，确认 mailbox 写入成功，再调整负责人或任务状态，是本页基于现有工具给出的稳妥次序。

5
完成与解锁
O

任务进入 completed 后，下游依赖自动解除。TaskCompleted hook 可以拒绝这次完成，并把理由送回执行者。

6
关闭与退出
O

Lead 给具名 teammate 发 shutdown request。对方可接受或拒绝。会话结束后 team config 自动删除，task 目录继续保留。

03

三股本地数据

运行成员

config 记录 lead、teammate 名字、agent ID 与 pane 等运行信息。程序会覆盖手工改动。

teams/{session-name}/config.json

定向消息

每个收件人有一个 mailbox。写入成功才算发送成功，无法写入会当场返回错误。

teams/{session-name}/inboxes/{agent}.json

共享任务

task 目录保存任务与依赖。team config 随会话退出清理；恢复后只有任务还在，in-process 成员需要重新拉起。

tasks/{session-name}/
I · 移交要分两步看。消息负责把上下文交给下一位，任务更新负责改责任与状态。交出工作的人应先写清已经查到什么，接手的人还要从哪一步继续。消息写入失败时，责任记录不宜先改，否则共享任务会显示有人接手，真正需要的上下文却留在原成员那里。官方没有承诺两份本地状态跨文件原子提交，所以页面不把它画成一次不可分割的动作。
04

权限门与停止点

开关门

默认关闭。没有实验环境变量，会话不会建立 team 目录，也不会拉起 teammate。非交互模式仍走普通 subagent。

权限门

Teammate 起步时继承 lead 的权限设置，后续请求显示在 lead 会话。来自另一个 agent 的批准说法不能代替用户同意。

质量门

TaskCompleted 可阻止任务完成。TeammateIdle 可把反馈送回去，让成员继续工作，也可明确停止该成员。

一致性门

任务状态偶尔会滞后，依赖任务随之卡住。Mailbox 无法写入时消息没有送达；两个成员改同一文件还可能互相覆盖。

登录与模型用量

Agent Teams 沿用当前 Claude Code 会话的凭据。首次运行或 /login 可以进入认证流程。Pro、Max、Team 与 Enterprise 使用 Claude.ai 账户，Console 使用受邀的 Console 凭据；Bedrock、Google Cloud 和 Microsoft Foundry 走各自的云端认证。

Pro 与 Max 的模型用量包含在订阅中，并受套餐限制。Team 与 Enterprise 从成员席位额度扣用量，这份额度还与 Claude chat 和 Cowork 共用。Console 与云提供商按 token 向组织计费。每个活跃 teammate 都有自己的上下文窗口，用量会随活跃人数和运行时间增长，直到成员退出或会话结束。用 /usage 查看当前口径，完成工作后及时关闭成员。

关闭请求不等于立即退出。Teammate 可以拒绝，也可能先做完当前请求或工具调用。Lead 需要等成员接受关闭，不能把请求发出当成已经退出。主会话的 lead 固定不变，成员不能再建嵌套 team。整个会话退出以后，运行成员配置会被清掉，任务记录仍按本机留存规则保留。

06

实现与版本断点

2.1.178移除 TeamCreate 与 TeamDelete，切到每会话一个隐式 team。
2.1.198API 错误退出的 teammate 会向 lead 报告 failed。
2.1.207畸形 mailbox 条目不再造成每秒循环报错。
2.1.224Mailbox 写失败不再误报为消息发送成功。

2.1.247 还继承了两处较近变化。2.1.199 调整了 idle teammate 在面板里的保留时间，2.1.234 移除了默认 teammate 模型设置。页面的生命周期结论按这些变更后的契约书写。

2.1.247 的最终回答有已知缺陷。Teammate 进入 idle 时，lead 可能只收到不带内容的可用通知。2.1.251 才把最终回答放进 idle 通知。本页固定在 2.1.247，移交步骤因此要求成员另发一条明确消息。

Dynamic workflow 的边界。它把编排写进 JavaScript 脚本，由 runtime 执行，适合更大的 fan-out。Agent team 仍由固定 lead 按共享任务和消息逐回合协调。本页不展开 workflow 自己的暂停、恢复和脚本状态。

07

还没有证据的地方

任务移交有没有原子保证

官方分别写了 task 更新和 mailbox 投递，没有承诺两者跨文件原子完成。页面只给出先传发现、再改责任的研究建议。

拒绝 shutdown 后 lead 怎样重试

官方允许 teammate 拒绝并附理由，却没有公开固定的重试次数、等待时间或升级到强停的默认状态机。

异常退出时先清哪一份状态

官方说明正常会话结束会删 team config 并留下 task。崩溃、强停和遗留 tmux pane 的精确清理次序未做真实实验。

2.1.247 的锁文件长什么样

官方承诺领取任务使用文件锁。本轮遵守隐私边界，没有查看个人 team 或 task 目录，也没有建立临时 team 来观察结构。

08

一手来源与复现

O · Agent Teams 官方指南证明隐式 team、任务、消息、权限、关闭、存储与限制。 O · 并行方式官方对比证明 team 与 subagent、Agent View、worktree 和 workflow 的边界。 O · Hooks 官方参考证明 TaskCompleted 与 TeammateIdle 的阻止和停止语义。 O · Dynamic workflows 官方指南证明脚本编排和共享任务编排的差别。 O · 认证官方指南证明订阅账户、Console 与云提供商的登录路径。 O · 用量与费用官方指南证明订阅额度、按 token 计费和 teammate 用量边界。 O · 官方仓库 changelog证明 2.1.178 以来与 team 直接相关的版本断点。 证据摘要已并入本页

安全复现需要固定 2.1.247，使用临时配置目录和空白仓库，先观察隐式 team，再核对争抢、依赖、消息失败和 shutdown。完成后删除整个临时环境。不要对个人 Claude 状态目录做这项实验。
