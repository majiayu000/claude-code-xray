最短答案

两套身份，四种 Provider。

CI 作业分别取得模型访问权和仓库回写权。GitHub Action 的官方云配方覆盖 Bedrock、Google Cloud 和 Foundry。GitLab CI/CD 的官方页只覆盖 Bedrock 与 Google Cloud，Foundry 组合仍是文档缺口。Provider 选择不改变仓库 token 的权限。O

先认四个配置点

同一个 job，身份分两路

模型身份回答请求发给谁、由谁计费。仓库身份回答谁能读写评论、分支和合并请求。OIDC 只是一张短期身份证明，云端还要有对应的 trust、role 或 service account。

01 / TRIGGER

触发配置

GitHub Action 可直接识别提及或接收自动化 prompt。GitLab 的评论提及通常要 listener 把 note 事件转成 pipeline trigger。

02 / MODEL ID

模型身份

API key、订阅 OAuth、Anthropic WIF、AWS role、Google service account 或 Azure Entra identity。它们不能代替仓库 token。

03 / REPO ID

回写身份

GitHub App、自建 App、GITHUB_TOKEN、CI_JOB_TOKEN 或 Project Access Token。权限太小时，模型成功也写不回去。

04 / PROVIDER

路由开关

Action 的三个 use_* 输入或 CLI 的 CLAUDE_CODE_USE_* 环境变量，把推理送往对应 Provider。

配置阅读顺序

先选支持格，再接两把身份

这里排的是部署配置的核对次序，不复述 runner 的执行状态。事件怎样启动作业、工具怎样循环和作业怎样停止，继续以 CLOUD-03 为准。

01 / SUPPORT

确认组合有官方配方

GitHub 可选 Anthropic、Bedrock、Google Cloud 和 Foundry。GitLab 官方页列出 Anthropic、Bedrock 与 Google Cloud，Foundry 这一格先留空。

02 / MODEL ID

绑定模型身份

直连路径保存 API key 或 OAuth token。云路径让 CI 的 OIDC token 换取 role、service account 或 Entra identity。

03 / REPO ID

另配仓库回写

GitHub 使用 App 或自动 token。GitLab 使用 job token，权限不足时再换 project token。模型身份不会扩大这套权限。

04 / EVENT

最后接触发和结果

GitHub Action 接提及或自动化事件。GitLab job 接 rules、MR、web 或 listener 转出的 trigger。回写位置由仓库 token 和工具许可共同决定。

身份与 secret 流向

两条凭据线在 job 里会合

模型线决定推理请求发往哪里，也决定模型费用归属。仓库线决定评论、分支和合并请求能否回写。两条线都进入同一个 job，权限仍彼此独立。OI

DOCUMENTED SUPPORT

GitLab 与 Foundry 留空

GitLab 官方 CI 页没有 Foundry 配方。通用 Azure 凭据链可以证明 Foundry 的认证入口，不能替这项组合补出支持声明。

SEPARATE PERMISSIONS

模型成功不保证回写成功

API key、role 或 service account 只处理模型请求。App、job token 与 project token 才决定仓库写入范围。

SETUP AND COST

开通权和账单分开核对

管理员先安装 App、保存变量或建立云侧信任。runner 计算与模型推理分别计费，页面只确认归属，不锁定实时金额。

VERSION PINNING

浮动版本会改变复现结果

@v1 会移动，GitLab 示例还可能在线安装新版 CLI。复现实验应固定 Action commit 和 Claude Code 版本。

NOT RUN / R

远端组合没有实际执行

配置 App、OIDC trust、CI variable 和模型账号会写入外部状态，也可能产生费用。本轮授权不包含这些动作。

SAFE REPRODUCTION

复现时逐格固定变量

在隔离仓库固定 Action commit 与 CLI 版本，每次只更换模型身份，仓库 token 保持不变，再记录触发和回写结果。

开通、登录与账单

配置前先确认谁有权，谁付费

CI job 通过 secret 或 OIDC 自动取得凭据，每次 run 无需打开交互式登录。管理员仍要提前安装 App、保存变量、建立云侧信任，并开通目标模型。runner 计算与模型推理分别计费。OI

GITHUB SETUP

仓库管理员先落配置

官方安装路径要求 repository admin access，用来安装 GitHub App、增加 secret 和提交 workflow。改用自动 GITHUB_TOKEN 可以省去 App 安装，权限与二次 CI 行为也会随之改变。

GITLAB SETUP

项目变量和回写权分开

直连 Anthropic 要保存 masked ANTHROPIC_API_KEY。仓库回写先用 CI_JOB_TOKEN，权限不足时才配置带 api scope 的 Project Access Token。

CLAUDE API

API 账单或订阅额度

API key 消耗 Claude API tokens。订阅 OAuth 适用于 Pro、Max、Team 和 Enterprise，run 占用生成该 token 的订阅额度。共享多个仓库时，官方建议使用组织 API key 或 WIF。

CLOUD ACCESS

云账号先开模型

Bedrock 要获准访问目标 Claude 模型。Google Cloud 要启用 Agent Platform API 并取得模型访问。Foundry 要已有资源和 Claude deployment。账单归属按配置所用云账号核对。

NON-INTERACTIVE

run 只消费预置身份

GitHub 从 repository secret 或 workflow OIDC 取凭据。GitLab 从 masked variable、job OIDC 或 WIF 配置取凭据。交互式登录只可能出现在前期人工配置，不属于每次 CI run。

RUNNER BILLING

计算分钟另算一笔

GitHub 托管 runner 消耗 Actions minutes。GitLab job 消耗项目所用 runner 的 compute minutes。两项都与 API、Bedrock、Google Cloud 或 Foundry 的推理账单分开。

未知项

矩阵里故意留出的空格

这些未知会改变部署与审计结论。没有官方声明或隔离实验，就继续留白。
