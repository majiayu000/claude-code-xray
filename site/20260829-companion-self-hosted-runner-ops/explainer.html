Self-hosted Runner 运维伴页

换一批 Runner，建议先接住容量再排空旧机

本页给出一套保守的 fleet 变更办法。运维方先确定谁能派发、会消耗哪份组织用量，再用隔离的 canary 验证新镜像。新容量的 poll 和会话启动都正常以后，旧 Runner 才停止接活并排空。这个顺序综合了官方的测试、扩缩容和排空契约，属于运维建议。 I 固定 fleet 的环境密钥对会话代码可读；on-demand 部署才能把长期密钥留在不执行会话的 orchestrator。 O

01 / terms

上线前先把五个控制点交给明确的人

01

产品准入

Owner 开启 Claude Code on the web 与自托管环境。CLI 派发还要登录 Anthropic 账户，并允许 remote sessions。 O

02

密钥保管

部署方决定采用固定 fleet 或 on-demand。这个选择决定环境密钥会不会落到执行会话代码的主机。 O

03

镜像与隔离

镜像固定 Claude Code 版本。每个 Runner 使用独立工作区，生产环境优先采用单会话临时容器或 VM。 O

04

容量与健康

容量按同时活跃的 owner 规划。进程存活、poll 新鲜度、活跃会话和版本需要分别观测。 O

05

凭据代理

内部服务校验 session JWT，再按单次编码任务签发最小权限凭据。长期云凭据不进入 Runner 镜像。 O

02 / sequence

一套保守的滚动替换建议

冻结变更条件

记录旧版本、base directory、capacity、drain 设置、停止宽限和回退镜像。 I

核对派发边界

确认套餐、Owner 开关、登录与组织策略，列清支持和暂不支持的启动入口。 I

部署 canary

新镜像使用临时文件系统和 capacity 1。固定 fleet 与 on-demand 使用各自的密钥路径。 I

跑 smoke test

在测试环境核对 dispatch、回复与 follow-up，确认新二进制能完成完整会话。 I

接入新容量

逐步增加新 Runner，观察 poll age、错误、活跃会话、capacity 和版本指标。 I

排空旧容量

向旧 Runner 发送 SIGTERM。它停止接活，再按 drain wait 处理手中的会话。 I

销毁并复核

确认子进程、hook 和 deregister 结束，再销毁旧工作区并检查 fleet 只剩目标版本。 I

管理页显示 Healthy 只说明控制面看到了 Runner。本页建议把 poll 新鲜、smoke test 成功、旧容量停止接活和旧工作区完成清理一并列入滚动替换的放行条件。官方分别公开了这些观测点与停止行为，没有规定这套完整放行顺序。 I

03 / flow

固定 fleet 会暴露环境密钥，on-demand 才能隔开

部署形态决定长期密钥的落点

固定 fleet 的每台 Runner 都持有环境密钥，会话代码能够读取密钥文件。on-demand orchestrator 不运行用户代码，可以保管环境密钥，并给新 Runner 一次性 work order。session JWT 则进入会话环境，用来标识指定环境、会话和创建者。 O

环境密钥文件

固定 fleet 把它放在 Runner 主机上，并按会话可读来防护。on-demand 形态把它留在 orchestrator。

CONTROL → API
Runner token

Runner 注册后取得，用来维持它与环境队列的关系。公开文档没有展开其格式和刷新细节。

API → HOST
仓库与工作区

Runner 在 base directory 下准备 checkout。生产加固建议让每个 Runner 使用独立、临时的文件系统。

GIT → DISK
Session JWT

会话子进程从环境变量取得。内部服务需独立校验签名、issuer、audience、role 和 expiry。

CHILD → SERVICE
事件与推理

控制面、会话事件流和模型推理仍走出站 HTTPS 到 Anthropic。Anthropic 不需要连入组织网络。

HOST → API
CHECK 01前缀与 ES256 签名
CHECK 02issuer 与环境 audience
CHECK 03session_worker role
CHECK 04expiry 与 creator act

有效 token 证明 Anthropic 为指定环境和会话签发了身份。它放在会话环境里，Claude 运行的代码、工具和 MCP server 都可能读取，因此它不能证明究竟哪个进程在出示。派生凭据要缩到一次编码任务需要的范围。 O

04 / limits

能不能派发、怎样计费、是否健康要分开判断

套餐与开关

Self-hosted environments 处于 Team 与 Enterprise public beta。Owner 要先启用 Claude Code on the web，再开启自托管环境；Zero Data Retention 组织不能使用。 O

登录与组织策略

终端派发需要 CLI 登录同一个 Anthropic 账户，并允许 remote sessions。配置为 Bedrock、Google Cloud Agent Platform 或其他第三方模型提供商时不可用。 O

组织用量照常消耗

自托管只把执行位置移到组织设施。会话消耗组织 Claude Code 用量的方式与 Anthropic 托管环境相同，自备算力不会换来免费云任务。 O

启动入口有明确边界

Web、移动端、Desktop、routine、终端和 Claude Tag 可以派发到自托管环境。Claude Tag 暂不支持 Access bundles；Claude Security 与 Code Review 暂不路由到这里。 O

派发范围

环境没有逐环境的派发访问控制。组织成员都能向任意环境派发。Runner 主机只能放这些派发者都有权读取的数据和凭据。 O

执行隔离

官方生产建议采用临时容器或 VM、`capacity 1` 和零 drain grace。更高 capacity 会让同一 owner 的多个会话共用容器资源。 O

健康探针

/healthz 在进程存活时总是返回 200。readiness 若只看状态码，抓不到卡死的 poll loop；还要看 poll age 和错误指标。 O

身份校验

wrapper 内的 decode 子命令只核签名与过期，不核 issuer、audience 或 role。用它做授权时，调用方还要逐项比较这些 claims。 O

正常完成

子进程结束，Runner 运行 post-session hook 并拆除 workspace。

默认 drain grace 为零，活跃会话结束后 Runner 退出。

收到 SIGTERM

Runner 先停止接新任务，再按 drain wait 处理手里的会话。

默认 drain wait 为零，会打断进行中的 turn；当前官方默认完整预算为 80 秒。 O

poll 消失

控制面在约 60 秒后把 lease 对应的会话重新排队。

这条路径不证明旧主机已清理，也不保证 hook 运行。 O

强杀或超时

剩余子进程与 hook 可能被一起终止，未推送工作可能丢失。

宿主的停止宽限要覆盖 Runner 启动时打印的总预算。 O

06 / implementation

扩容、升级与退役都要顾及活跃 lease

SCALE

扩缩容先数 owner

一台 Runner 同一时刻只服务一个 owner。capacity 增加的是这个 owner 的会话并发，不会跨 owner 拼容量。 O

  • 固定 fleet 可按 active sessions 与 capacity 指标扩缩
  • on-demand orchestrator 为排队任务调用 spawn hook
  • 预热 slot 要配合 unused timeout 回收
UPGRADE

升级替换 Runner

会话子进程使用 Runner 自身的二进制，子进程自动更新被关闭。新版本要进入镜像或宿主，再重启 Runner。 O

  • 同一环境保持相同 base directory 与 capacity O
  • 新镜像先在测试环境跑完整 smoke test O
  • 滚动替换前设置 drain wait 与宿主宽限 I
RETIRE

下线先撤容量

Runner 收到 SIGTERM 后停止接新任务。给它时间结束 turn、停止子进程、运行 hook 和 deregister，最后再销毁主机。 O

  • 默认 drain wait 为零，滚动重启会打断 turn
  • 固定寿命主机可提前设置 retire time
  • 强杀会跳过剩余清理并触发稍后的重排

实际部署可以让一批新 Runner 接替旧 Runner，再用 fleet 的版本和健康指标检查替换过程。这是依据官方固定版本、重启生效和排空契约得出的运维读法。 I

07 / unknowns

这些地方还不能写死

Runner token 怎样刷新和撤销

官方只说明 Runner 注册后取得 token 并开始 poll，没有公开它的格式、内存驻留方式、刷新时点和服务端撤销机制。

多台空闲 Runner 的选择算法

官方说明有空位的 Runner 会领取 lease，也说明 owner 锁。相同 owner、相同 capacity 的多台 Runner 之间怎样排序，没有公开。

管理页删除环境时的精确顺序

测试文档给了专用测试环境的删除接口，生产运维页没有完整说明删除或禁用环境时，活跃 lease、Runner 与会话依次会怎样变化。

真实强杀会丢多少工作

官方明确警告未推送工作和 hook 可能丢失。不同容器运行时、停止宽限和中断时点的结果，需要一套可销毁 fleet 做 R。

2.1.247 的本机完整 help

当前 shell 没有解析出 claude，可执行调用也被环境策略拦截。本轮无法把固定基线的参数和默认值与 live docs 再核一遍。
