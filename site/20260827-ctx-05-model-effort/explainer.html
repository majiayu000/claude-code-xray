模型选择与 effort

切换改的是下一次请求。

Claude Code 先确定会话当前使用的模型，再确定这个模型能接受的 effort。你在会话里改动其中一项，旧消息仍然保留，下一次请求采用新组合，并重新处理整段对话缓存。O

选择还要穿过账户资格、组织 allowlist 与 provider 部署三道门。套餐会改变默认模型和 1M 上下文的付费方式，第三方 provider 缺少默认部署时，有的会回退，有的直接报错。

01 · TERMS

三个词够用了

本页只跟踪主会话怎样选模型与 effort，Fast Mode 和 Advisor 有自己的路由状态，留给 CTX-06。

MODEL

模型选择

可以是 Claude 模型别名、完整模型名，也可以是 Bedrock ARN 或 Foundry deployment name 这类 provider ID。O

EFFORT

每次请求的用力程度

low 到 max 影响整次响应可能投入的 token，也会影响工具调用与思考。ultracode 是另一项 Claude Code 设置，它给模型发送 xhigh，还会为实质任务编排动态工作流。O

ACTIVE PAIR

当前组合

模型和 effort 一起决定下一次请求的执行条件，也一起参与缓存键。组合变化会让下一次请求失去旧缓存命中。O

02 · SEQUENCE

一次会话中切换的时间顺序

命令本身先改当前选择，费用、延迟和输出差异到下一条模型请求才出现。

会话先拿到初始模型

启动参数优先于 shell 中的模型变量，后面才看 settings 与默认选择。组织策略仍能限制最终可选范围。OL

Effort 另走一条解析线

CLAUDE_CODE_EFFORT_LEVEL 压过会话命令和 settings。模型不支持所选等级时，Claude Code 向下落到受支持的最高等级；组织 cap 还可能继续压低。2.1.247 也接受 --effort ultracode，这条入口从 2.1.203 起可用。环境变量和持久 effortLevel 不接受该值。O

用户在会话中切换

/model 或 /effort 修改活动组合。旧缓存仍温热时，终端会先确认一次冷缓存成本；缓存过期后直接切换。O

下一条消息触发新请求

Claude Code 保留旧对话，把完整上下文交给新的模型与 effort。新组合没有旧缓存命中，首个响应通常更慢，输入处理成本也更高。O

后续请求沿用新组合

新缓存建立以后，后续回合继续使用当前组合，直到再次切换、退出或恢复时重新解析。Telemetry 可以记录每次请求实际使用的 model 与 effort。O

03 · FLOW

从选择入口到 provider 边界

直接调用 Anthropic API 时可以确认 Messages 字段。第三方 provider 只确认部署 ID 与失败规则，完整序列化形态仍未知。

输入选择

/model、--model、环境变量或 settings 给出模型。Effort 有对应的会话命令、启动参数、变量与 settings。

→
本地解析与权限门

Claude Code 解析别名，检查组织 allowlist，并按模型支持范围与组织 cap 修正 effort。第三方 provider 的模型名会落到 inference profile ARN、version name 或 deployment name。O

→
下一次远端请求

直连 Anthropic API 时，Messages 契约把两个选择放进不同字段。O

modelAnthropic 模型名
output_config.effort最终 effort 等级

Bedrock、Google Cloud 与 Foundry 的完整请求形态没有在本轮验证，不能照搬这两个字段。I

模型 ID 与 effort 最终值可以出现在请求 telemetry。模型不支持 effort 时，相关属性会缺席。O Claude Code 内部怎样把活动选择交给各 provider 适配器没有公开。I

04 · LIMITS

三道门决定选择能否落地

用户选中的名字只是候选，账户、组织与 provider 都可能改变结果。

套餐与席位2.1.247 的运行时默认值按账户分开。Max、Team Premium、Enterprise 按量付费与 Anthropic API 默认 Opus 5；Pro、Team Standard 与 Enterprise 订阅席位默认 Sonnet 5。组织默认和 allowlist 仍能改写结果。O
1M 上下文Max、Team 与 Enterprise 的 Opus 1M 含在订阅内；Pro 走 usage credits。Sonnet 4.6 的 1M 在所有订阅套餐上都要 usage credits。API 与按量付费账户按用量计费。该资格检查只发生在直连 Anthropic API 时。O
组织策略availableModels 限制模型范围。每模型 effort cap 会把过高等级压到角色允许的上限。
ProviderBedrock 与 Google Cloud 的默认模型未部署时会提示并回退到旧版，Opus 全部不可用时再落到默认 Sonnet。Foundry 没有同等的启动检查，缺少部署时直接报错。O

失败与停止位置

  • 会话内选到组织禁止模型，切换直接被拒绝，当前模型继续留用。O
  • 启动入口选到被挡模型，Claude Code 会警告并换回默认模型。O
  • settings 或环境变量写错模型名，部分路径到第一次请求才报模型问题。O
  • Effort 太高时可能向下兼容或被组织 cap 压低，最终值未必等于输入值。O
  • Bedrock 与 Google Cloud 可从缺失的内置默认模型回退；Foundry 没有这条启动回退，会报错。显式固定的具体版本会跳过前两者的默认模型检查，版本是否可用留到请求处理。O

06 · IMPLEMENTATION

持久选择和会话选择分开看

2.1.247 里，交互式命令通常还会影响以后新会话，启动参数只管这一次，恢复旧会话另有模型继承规则。

/model

直接输入模型名会切换，并保存为新会话默认。Picker 按 s 才只改当前会话。项目或 managed 初始值会在下次启动重新施加。O

--model 与环境变量

它们只影响这次启动。显式启动选择还能覆盖恢复会话保存的模型。OL

/effort

low、medium、high 与 xhigh 可以跨会话保存，max 通常只留在当前会话。ultracode 单独保存在同名设置中；工作流关闭时，该入口只留下 xhigh effort。O

恢复会话

Anthropic API 通常恢复 transcript 里的模型。Bedrock、Google Cloud provider 与 Foundry 的 provider-specific 模型 ID 重新走正常解析。O

2.1.153/model 默认保存
2.1.195组织 effort cap
2.1.200宿主 setModel 识别
2.1.203--effort ultracode
2.1.238切换确认检查 TTL
2.1.247修复 picker 快速按键
07 · UNKNOWNS

这些地方还没有运行证据

缺口主要来自账户资格、远端策略和真实请求，它们不能靠读取本机私人会话来补。

当前账户能看到哪些模型

本轮没有登录会话，也没有打开 picker。官方契约说明可见项受套餐、席位与组织策略影响，当前账户的具体列表仍未知。

第三方 provider 收到的完整请求体

官方 API 已公开 model 与 effort 的语义。Claude Code 对 Bedrock、Google Cloud provider、Foundry 与自定义 gateway 的完整序列化差异没有在本轮观察。

命令确认、取消与 settings 写入 diff

没有运行 /model 或 /effort，所以本机 2.1.247 的实际文案、取消后的状态与写入差异没有 R。

组织 cap 与 gateway 的组合结果

远端组织策略内容没有读取。自定义 gateway 是否转发 effort、接受哪些模型名以及怎样计费，也要由 gateway 契约和授权实验确认。
