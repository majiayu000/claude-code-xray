CLAUDE CODE XRY · 2026-08-27 基线

本地提交和创建 PR 是两步

Claude Code 可以看 Git 状态、改文件、跑测试并做本地提交。提交还留在你的机器上。推送分支和创建 PR 会碰到第二道闸，远端认证、仓库写权限和服务端规则都得放行。

当前状态 documented Claude Code 2.1.247 无远端写入实验 首屏结论 O + I
一次请求没有自动变成一笔原子事务。

检查、编辑、测试、提交、推送和建 PR 是相邻步骤。后一步失败，前一步可能已经留下文件、提交或远端分支。

工作树与本地 Git 远端分支与 Pull Request
01 / TERMS

先认清四份状态

它们分别写入，可以同时存在，也不会被一次失败统一回滚。读懂这四份状态，失败停在哪里就很清楚。

工作树

磁盘上的当前文件。Claude 的 Edit、Write 或 shell 命令会改这里，尚未必进入暂存区。

暂存区与提交

Git 选择要进入提交的内容，再把快照和消息写进本地仓库。提交成功仍然不等于已经上传。

远端分支

git push 把本地提交送到仓库 remote。网络、凭据、写权限和分支规则会在这里介入。

Pull Request

gh pr create 在 GitHub 建一条协作记录，带上 head、base、标题与说明。它是远端对象。

02 / SEQUENCE

一条常见路线

官方材料确认这些能力，也给出一条打包命令路线。普通自然语言请求仍由 Claude 按仓库现状选命令，官方没有公开固定的规划算法。

01读状态status · diff · log
02改文件Edit · Write · Bash
03跑测试仓库脚本与退出码
04暂存选择进入提交的文件
05本地提交新 HEAD 与 hooks
06推送分支remote · auth · rules
07创建 PRgh · base · head · URL

O 官方 /commit-push-pr 命令集把后半程写得很具体。处在主分支时建新分支，随后暂存和提交，推送到 origin，用 gh pr create 建 PR，最后给出 URL。它要求 GitHub CLI 已安装并认证，仓库也要有 remote。

O + I 用户仍然握着两个分开的决定。一个决定 Claude Code 可以在本机执行哪些 Bash 命令，另一个决定当前认证身份能否写入目标仓库。在本地权限提示里放行 git push 之后，远端仍会核对凭据和仓库权限。gh 已经登录也不会让本地 deny 规则失效。

03 / FLOW

两道闸检查不同的东西

本地允许执行一条命令，不能替代远端对身份和仓库的判断。两道闸都放行，数据才会从工作树走到 PR。

本地场 O

  • 只读形式的 Git 通常无需提示
  • 文件编辑受当前 permission mode 控制
  • 测试、暂存与提交走 Bash 权限
  • deny 规则会压过 ask 与 allow
REMOTE GATE

远端场 O + I

  • Git 或 gh 要有可用认证
  • 当前身份要能写目标仓库
  • remote、head 与 base 必须成立
  • 服务端规则、CI 和分支保护继续生效
O + I · CLAUDE ACCESS

先登录，Claude 的用量也要有出处

终端版 Claude Code 首次使用前要完成认证。官方列出的入口包括 Pro、Max、Team 或 Enterprise 订阅，带预付费额度的 Console 账户，以及受支持的云提供商。它们承担 Claude Code 本身的访问与计费。GitHub CLI 的登录是另一件事，只负责后面的 GitHub 身份。

O · SURFACE SCOPE

本页只核对 CLI 与 GitHub 路线

页面里的权限参数、Bash 命令和 gh pr create 都来自终端 CLI 路线。官方还提供 Desktop、VS Code、JetBrains 和 Web，各处的执行环境与交互方式会变。本轮没有逐项验证这些界面，也没有验证 GitLab 的 MR 与 CI/CD 路线，不能把这里的提示位置和命令顺序原样外推。

04 / STOP POINTS

失败会把状态留在原地

最实用的排查办法是看最后成功的是哪一步。那一步以前的状态通常还在。

O · LOCAL PERMISSION

编辑或 Bash 被拒绝

工具调用不执行。官方说明，主会话的权限提示若选择拒绝且不加说明，本轮会停；加上说明后 Claude 可以收到原因再继续。

O + I · TESTS & HOOKS

测试或提交钩子失败

修改仍在工作树或暂存区。官方只承诺在可用时运行测试，具体脚本、签名与 hook 都由仓库决定。

O + I · REMOTE AUTH

推送失败

本地提交仍可存在。常见关口落在凭据、remote、网络、仓库写权限和远端分支规则。

O + I · PR CREATE

建 PR 失败

远端分支可能已经推上去。官方工作流要求 gh 已认证，官方也没有承诺在建 PR 失败时自动删掉远端分支。

I 排查时可以依次查工作树、暂存区、本地 HEAD、远端分支和 PR 列表。测试失败常会留下未提交的修改，提交 hook 失败时暂存内容可能还在。推送失败一般不会撤销本地提交，建 PR 失败也可能保留已推送的分支。这是根据分步顺序得到的排查方法。官方没有承诺自动恢复这些状态。

因此，本页可以证明入口和约束，还不能证明 Claude 面对某个仓库时会把图中七步全部执行。页面要升为 verified，需要在隔离的测试仓库里记录真实工具调用、权限提示和 Git 前后状态。推送与建 PR 还要等测试远端获得明确授权后再验证。

07 / UNKNOWNS

还不能写死的地方

这些缺口会改变你能不能把流程跑到最后，留着比猜一个答案更有用。

具体仓库里会选哪些命令

官方给出能力和配方，没有公开一个对所有提示都不变的命令规划算法。Claude 可能按仓库脚本、已有修改和你的要求调整检查与测试。

2.1.247 会话里是否启用了 commit-commands

固定二进制带有插件管理入口，官方仓库也有这组命令。本轮没有启动会话或读取私人插件配置，实际启用状态未知。

远端身份与仓库规则会怎样回应

本轮没有查看 gh 登录、仓库 remote、可见性、写权限或分支保护。安装了 gh 只说明命令存在。

其他界面的权限与 Git 路线是否相同

官方说明各界面共用底层 agent 循环，但 Desktop、IDE 与 Web 的执行位置和交互方式并不相同。GitLab 走 MR 与 CI/CD 集成。本页没有验证这些界面的具体提示、认证或回滚行为。

后一步失败后会不会自动清理

官方材料把提交、推送和建 PR 分步列出，没有给出跨 Git 与 GitHub 的原子回滚承诺。
