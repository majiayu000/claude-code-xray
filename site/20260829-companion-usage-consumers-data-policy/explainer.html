伴页成本、团队分析与数据政策矩阵

一条动作，三本账

Claude Code 的一次使用，会在成本侧变成 token 与金额，在团队侧变成按日汇总的会话、接受率和代码贡献，在数据治理侧继续受账户类型、组织路由与功能范围限制。三处口径不同，保留期也不会自动相同。官方资料没有把它们描述成共用一份物理 event。

OTel 事件如何产生、含有哪些字段、怎样导出，由 ADM-06 负责。本页从消费端接手，比较估算、日聚合和政策约束。

01Terms

先分清记录的口径

USAGE EVENT

使用动作

一次 session、prompt、模型请求或工具决定。它在不同消费面可以形成多个派生数值。

ESTIMATE

成本估算

token 乘价格得到的参考金额。`/usage` 与 OTel cost metric 都不能替代 provider 账单。O

DAILY AGGREGATE

日聚合

Analytics 把同一 UTC 日内的会话、工具接受与 token 按用户或 API key 汇总。O

RETENTION SCOPE

保留范围

某条政策覆盖哪些产品、数据与组织。ZDR 只覆盖已路由到合格组织的 inference。O

本页所说的“同一条”

它指同一用户动作的业务含义。官方没有公开一条跨 OTel、Analytics 和账单系统通用的 event ID。把三处强行 join 成一条物理记录属于推断，本页不这样画。

I 可靠做法是分别核对日期、用户身份、provider 和模型，再承认延迟与估算误差。

02Sequence

先计一次使用，随后各自结账

下面只写官方能够支持的先后。中间没有画一条共用的远端事件总线。

用户开始动作

会话、prompt、模型请求和工具决定按各自生成点发生。

请求完成

token、模型和身份口径可用于会话估算或后续汇总。

本地估算

`/usage` 根据 token 与价格表计算。数值仍是参考。O

组织自建观测

显式配置 OTel 后，客户 backend 可按用户、团队与模型归因。O

Analytics 聚合

日会话、接受率、代码行与成本按产品契约刷新。O

政策继续生效

保留、训练、ZDR 与第三方例外跟随账户和数据面。O

费用停止累计，不代表 Analytics 立即刷新；ZDR 清掉 inference 留存，也不会清掉 Analytics 的 productivity metadata。

03Consumer matrix

三种消费面，六个判断口

比较口成本团队分析数据治理
聚合 会话内按模型统计 token，再换成估算金额。OTel 还能按用户、团队、skill、plugin 或 agent 分组。 仪表板看日活、session、接受率和代码行。Admin API 按单个 UTC 日逐用户或 API key 返回。 按账户类型、组织和产品面套用政策。Inference、Analytics、本地 transcript 与第三方后端分别判断。
时间 `/usage` 随会话更新，`/clear` 在 2.1.211 起重新计数。权威账单跟随 provider。 贡献数据通常在 24 小时内出现并每日更新。Admin API 官方给出最多一小时延迟。 Consumer 训练开启时五年，关闭时 30 天。Commercial 标准 30 天。ZDR inference 响应后不保留。
身份 本地会话、OTel attributes、Console workspace 或 provider 账户各有自己的归因键。 OAuth 用户以邮箱表示，API 用户以 key 名表示。贡献指标只覆盖 claude.ai 组织用户。 ZDR 取决于请求是否进入已启用的组织。个人登录或另一组织 key 会落到别的政策。
脱敏 成本数值可以不含正文，仍能暴露用户、模型与使用强度。OTel 具体字段回到 ADM-06。 ZDR 下 Analytics 不存 prompt 或 response，仍收集邮箱和 usage statistics。 商业数据默认不用于训练，客户明确选择提供数据时例外。ZDR 也保留法律和违规处理例外。
权限 API 组织由 Console workspace limit 和账单角色管理。provider 账单权限另算。 Team 与 Enterprise 由 Owner 或 Admin 查看。贡献指标还需要 Owner 与 GitHub 管理员配合。 ZDR 需要 Anthropic 单独启用，并按组织生效。客户端开关无法独自获得这份政策。
停止与失败 预算或用量限制可以停止新请求。估算与账单不一致时，以 provider 为准。 角色不够会挡住查看。GitHub 未连接、仍在处理或 ZDR 会让贡献面缺失。 ZDR 组织会在服务端挡住依赖保存 prompt 或 completion 的功能。第三方集成仍按自己的规则处理。

04Limits

ZDR 只剪掉它覆盖的那一段

INFERENCE

已覆盖的部分

合格 Enterprise 组织启用 ZDR 后，已路由进该组织的 Claude Code prompt 与 response 在返回后不由 Anthropic 保存。O

ANALYTICS

仍然留下的部分

Analytics 继续收集邮箱与使用统计。贡献指标停用，usage metrics 继续显示。O

OUTSIDE

另行负责的部分

第三方工具、MCP、组织 OTel backend 和其他 provider 服从各自的数据处理规则。O

  • 角色门没有相应 Owner、Admin、Billing 或 UsageView 权限，用户看不到对应仪表板或 API。
  • 组织门ZDR 按组织开启。新组织要单独启用，身份路由错误会让请求落出范围。
  • 功能门ZDR 会在服务端禁止需要保留 prompt 或 completion 的 Web、云会话、反馈和 Remote Control 等功能。
  • 政策例外法律要求和 Usage Policy 违规处理可能让相关输入输出保留最多两年。

保留边界

三处是同一动作的派生视图。官方没有承诺一条共用物理 event。

版本边界

本页固定 Claude Code 2.1.247。`/usage` 的 `/clear` 清零规则有官方版本线，2.1.211 起生效。Analytics 和 ZDR 主要由服务端与组织策略控制，单看客户端版本无法证明权限、延迟和保留期。

官方网页持续更新，没有 2.1.247 的冻结页面。本页记录 2026-08-30 读到的公开契约，并把无法锁到客户端发布日的字段留作版本限制。

07Unknowns

仍有五块不能写死

三处有没有共同 event ID

官方没有公开跨 OTel、Analytics 和账单系统的通用标识、去重键或事件总线。

Analytics 历史数据何时删除

Claude Code Analytics API 文档明确说历史数据可访问，同时没有给删除期限。

迟到数据怎样回补

官方给了最多一小时、每日刷新或一天延迟等 freshness 说明，没有公布完整修订窗口。

客户 backend 怎样保留

组织 OTel 导出后的字段过滤、保留、删除与访问审计由部署方决定，没有统一的 Anthropic 答案。

ZDR Analytics 的逐字段期限

官方确认邮箱和 usage statistics 仍会收集，没有给 2.1.247 冻结字段表或逐字段保留期。

08Sources and reproduction

证据从哪里来，怎样重做

  • Monitoring 文档，证明 OTel 成本估算、归因维度和客户 backend 边界
  • 成本管理文档，证明 `/usage` 估算、价格表、清零版本与权威账单入口
  • 团队 Analytics 文档，证明指标、角色、GitHub 范围和刷新节奏
  • Analytics API 文档，证明 UTC 日聚合、用户粒度、延迟和 provider 范围
  • Data usage 文档，证明训练选择、账户保留期与本地 transcript 边界
  • ZDR 文档，证明组织路由、覆盖数据、Analytics 例外和服务端限制

最小对照

固定 2.1.247，用两个合成身份和不含代码的 prompt。分别记录 `/usage`、最小 OTel、provider 账单与下一 UTC 日的 Analytics，只保存匿名摘要。

ZDR 对照

取得合格测试组织与 Anthropic 明确启用后再做。检查 usage metrics 是否保留、贡献面是否缺席、依赖留存的功能是否由服务端拒绝。

两组实验都需要登录，可能产生订阅或 API 用量，也会触及组织设置。本轮只记录复现方法，没有执行。
